1. Why is a pipeline stage that fails silently worse than one that crashes loudly, for something whose whole job is to respect the rules before acting? Explain the connection with CM3's provenance argument?

A silent failure is more dangerous because the pipeline may continue without warning, even though it has not correctly checked whether scraping is allowed. As a result the data could be collected without respecting the website's access rules. This also creates a provenance problem because we cannot reliably explain how the data was acquired or whether the access conditions were properly checked.



2. What is the actual difference in risk between France Travail's API data and this jobspy-derived sample? Would your answer change if the repository were private instead of public, and why does public/private matter?

France Travail provides official government open data with licence but jobspy-derived data comes from scraping platforms whose terms may restrict the redistribution of collected data. A public repository increases the risk because anyone can access and reuse the scraped data. A private repository reduces public exposure, but it does not automatically make data collection or storage compliant with the platforms' terms.


3. Why is converting free text into a structured list of skills a good task for an LLM, while recording your actual application actions is not?

Job descriptions contain unstructured text, different writing styles. An LLM is useful because it can understand this context and extract relevant skills into a structured list. However, recording my actual applications should rely on explicit records or database operations because these are factual actions that must be tracked accurately, not inferred by an AI model.


4. What formatting inconsistency did you expect across independent LLM calls? Did you find an example in your extracted.json?

Before checking the results, I expected the same skill to appear with different capitalization across independent extraction calls. I found this with "Generative AI" and "generative AI" in my extracted data. If these variants are not normalized, the same skill could be counted as two separate categories and affect the accuracy of the KPI.

5.Why does a second person reviewing the model's raw output against the original source text count as human-in-the-loop? Why must this check happen on extracted.json rather than kpi.json?


A human-in-the-loop process means that a person checks and validates the output generated by an AI model instead of accepting it automatically. The review must happen on extracted.json because it contains the skills extracted from each individual posting, making it possible to compare them with the original descriptions and identify missed or hallucinated skills. The final kpi.json only contains aggregated results, so it does not provide enough detail to identify which individual extraction was incorrect.


6. Which single skill would you choose to track first for ENSIM's curriculum committee, and why? After changing TARGET_SKILL to your choice, which KPI value would you trust for a real decision: the default, your own choice, or neither?


I would choose Python because it is a fundamental programming language for data engineering, artificial intelligence and machine learning. In my extracted sample, Python appears in 2 out of 12 postings, giving a KPI value of 17%. Since Python is also the default target skill in the provided script, both KPI values are identical. I would use this result as an initial indication, but neither value alone is sufficient to make a curriculum decision because the sample is small and does not necessarily represent the entire job market.



7. Could someone reconstruct the specific postings or companies from your published kpi.json? What information did you leave out, and was this a deliberate design choice?



The published kpi.json does not directly identify the companies or individual job postings because it contains only aggregated information, such as skill names, counts and KPI values. I deliberately excluded company names, job titles and original descriptions when designing the published output. However, rare skill combinations could still provide clues about the type of posting, so aggregation reduces the risk of identification but does not guarantee complete anonymity.
